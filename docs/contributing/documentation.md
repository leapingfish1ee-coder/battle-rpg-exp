# 文档维护规范

## 1. 范围

本规范约束 `docs/` 下的长期项目文档，并用于保证架构、视觉方向、实现与历史技术决策之间保持可追踪关系。

## 2. 文档类型

- `docs/architecture/`：描述当前有效的系统事实、模块边界、数据流和运行机制。
- `docs/art-direction/`：描述当前有效的项目美学、视觉语言、画面质量、渲染表现和后处理约束。
- `docs/adr/`：保存不可覆盖的架构决策历史。
- `docs/contributing/`：保存研发流程、文档规则和协作约定。
- 后续如引入协议、数据格式或生成型参考资料，可增加 `docs/reference/`。

## 3. 写作要求

1. 文档首先描述约束、边界和事实，不以教程式叙事替代设计说明。
2. 模块名称、目录路径、协议名称和状态名称必须与代码保持一致。
3. 架构文档不保存已经失效的争论，历史原因由 ADR 承担。
4. Art Direction 文档必须把“高级感”“精致”“庄重”等主观目标拆成颜色、构图、材质、字体、动画、渲染质量、后处理或评审条件等可执行约束。
5. 避免只写“高性能”“可扩展”“高画质”等无法验证的目标，必须给出对应机制或度量。
6. 示例代码只用于表达契约或数据流，不应成为另一份无法执行的实现副本。

## 4. 何时更新文档

以下变化必须同步更新文档：

- 新增、删除或改变架构层；
- 改变模块依赖方向；
- 改变状态所有权或真值来源；
- 改变游戏循环、Simulation tick 或渲染数据流；
- 改变 Scene、资源、网络、存档或 Worker 生命周期；
- 改变客户端/服务端协议兼容策略；
- 引入会长期限制实现方式的核心依赖或基础设施；
- 改变项目主体美学、色彩体系、角色比例、UI 语言、材质方向、渲染精度策略或全局后处理原则。

## 5. 何时新增 ADR

出现以下情况之一时新增 ADR：

- 存在两个以上合理候选方案且取舍会长期影响维护成本；
- 决策改变模块边界或数据所有权；
- 决策引入不可轻易回滚的运行时、协议或存储约束；
- 决策取代已有 Accepted ADR；
- 未来维护者仅查看代码无法可靠理解“为什么必须这样做”。

单纯的美学方向调整通常更新 Art Direction 文档；如果视觉方案同时引入长期运行时约束、核心渲染依赖或不可轻易回滚的 GPU 管线，则还必须新增 ADR。

## 6. 评审检查

文档变更应检查：

- 是否与当前代码或计划实现一致；
- 是否出现相互矛盾的系统真值或视觉真值描述；
- 是否需要新增或更新 ADR；
- 是否破坏已有文档链接；
- 是否明确使用 MUST、SHOULD、MAY 或等价自然语言区分强约束与建议；
- 是否存在可通过自动化规则验证但仍只写在文档中的架构或视觉限制。

## 7. 生命周期

- Architecture 文档持续更新为当前系统状态。
- Art Direction 文档持续更新为当前视觉真值，重大方向替换必须在同一变更集中说明迁移影响。
- ADR 保留历史并通过状态关系演进。
- Contributing 文档随研发流程变化直接更新。
- 已废弃文档应删除或明确标记 Deprecated，禁止让失效设计与当前设计并列而不注明状态。

## 8. 自动化方向

架构与视觉规范中能够机器验证的限制应逐步迁移到 ESLint、TypeScript、Schema validator、测试或 CI，例如禁止 `domain/` 和 `simulation/` 导入 `pixi.js` 的约束应由静态规则执行，重复交互后的像素稳定性、固定 viewport 的视觉 baseline 和质量档配置完整性也应由自动化验证，文档只定义规则语义。
